MazenOS / Getting started

Your space, ready to connect.

This guide takes you from the ZIP to your own Cloudflare website. The application code is complete, but you must create the Cloudflare resources, configure secrets, then connect your phone. Keep your existing Taskitator installation separate.

Use a new repository and new database.

The old Taskitator app uses a different account and storage system. This is a fresh MazenOS installation with empty tables. Uploading these files into the old repository could leave incompatible old workflows or assets in place.

1. Create the two data resources

  1. In Cloudflare, open Storage & databases → D1. Create a database named mazenos. Copy its database ID.
  2. Open Workers KV. Create a namespace named mazenos-temp. Copy its namespace ID.
  3. In the ZIP’s wrangler.toml, replace REPLACE_WITH_D1_DATABASE_ID and REPLACE_WITH_KV_NAMESPACE_ID with those IDs. Keep the binding names DB and TEMP.
  4. Choose a unique Pages project name, such as your own mazenos-yourname. Set ALLOWED_ORIGINS in wrangler.toml to its exact website origin, e.g. https://mazenos-yourname.pages.dev. No trailing slash.

The deployment workflow applies schema.sql to D1 for you. It contains no sample records. Do not point it at the existing Taskitator database.

2. Set up GitHub deployment

  1. Create a new GitHub repository. Unzip the project and upload its contents directly to the repository root. Confirm worker.js, schema.sql and index.html are at the root, and the workflow is at .github/workflows/deploy.yml.
  2. Use a main branch named main. The workflow runs on pushes to that branch and can also be run manually under Actions.
  3. In Cloudflare, create an API token limited to your account with Workers Scripts: Edit, D1: Edit, Workers KV Storage: Edit and Cloudflare Pages: Edit. Cloudflare may label these as Write permissions in its API reference.
  4. In GitHub → Settings → Secrets and variables → Actions, add the following.
TypeNameValue
SecretCLOUDFLARE_API_TOKENThe deployment API token you just created.
SecretCLOUDFLARE_ACCOUNT_IDYour Cloudflare account ID, from the account overview.
VariableMAZENOS_PAGES_PROJECTYour unique Pages project name.
VariableMAZENOS_API_URLhttps://mazenos.YOUR-WORKERS-SUBDOMAIN.workers.dev. Find your Workers subdomain in Cloudflare Workers & Pages. If this is your first Worker, Cloudflare may ask you to choose one.
  1. Run Actions → Deploy MazenOS → Run workflow. The workflow checks the code, runs tests, applies the schema, deploys Worker mazenos, creates the direct-upload Pages project if needed, builds only public assets and deploys them.
  2. Open the Worker in Cloudflare and check its actual workers.dev URL. If it differs, correct GitHub variable MAZENOS_API_URL and rerun the workflow.

Once this setup is complete, normal updates are an upload or push to GitHub. No separate Worker text file needs to be uploaded to Cloudflare. The first deployment remains unable to create an account until you add the setup secret below.

3. Add the server secrets

In Cloudflare → Workers & Pages → mazenos → Settings → Variables and Secrets, add these as Secret values, then deploy/save the configuration:

SecretWhat to use
SETUP_TOKENA long random one-time setup code. Keep it private. Use at least 32 random characters.
VAULT_KEYExactly 64 random hexadecimal characters. This encrypts your AI keys. Back it up securely and keep the same value on updates.

To generate random values locally with Node, run either command twice as needed. Each produces 64 random hex characters; use separate values for the two secrets:

node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"

Do not put either value in GitHub source files, screenshots or this guide. Worker secrets remain in Cloudflare across normal code deployments.

4. Open MazenOS for the first time

  1. Open your Pages website. The login page should have the correct Worker address filled in.
  2. Choose your master password with at least 12 characters.
  3. Expand First-time setup and enter your SETUP_TOKEN. Press Continue.
  4. Open Settings. Add your Gemini and/or Claude API key, confirm with your new master password and press Save keys. Select a provider and Light or Smart tier.
  5. Set your rest windows in Riyadh time. Open Settings from Curry to set your daily focus allocation; open it from Tasks to set the default focus timer.
  6. After successful setup, you may delete SETUP_TOKEN from Worker secrets. The existing password prevents a second setup even while the code remains configured.

The app is empty by design. Create one real task and one health check-in to begin. The provider keys are saved on the server; you do not have to re-enter them per tool or device. Each new browser session signs in with the same master password.

5. Connect MacroDroid

Open Settings → Phone → Create phone token. Confirm with your master password, copy the once-only token and follow MACRODROID.html. One phone token covers status, bank SMS, NewPipe titles and energy sync. It cannot read your private tools or keys.

Start with the overlay macro disabled. Verify that the phone can poll status and that recovery/rest unlocks work. Then enable the overlay with a clear manual recovery route.

Set the public Worker URL in config.js before a manual build, or provide MAZENOS_API_URL as an environment variable. The GitHub workflow handles this automatically. Do not upload the repository root as the Pages directory: deploy only dist.

Custom domains

Add the website’s exact HTTPS origin to ALLOWED_ORIGINS in wrangler.toml. If your Worker uses a custom API domain instead of workers.dev, add that API origin to connect-src in _headers, update MAZENOS_API_URL, and redeploy. Do not set CORS to *.

Backups and password recovery

Use Settings → Download data for a human-readable export. It excludes API keys, tokens and password hashes. The app does not include a bulk restore interface; use D1 exports/backups for full database restoration. Keep VAULT_KEY separately if you need to recover encrypted provider keys.

If you forget your master password, first disable the phone overlay and back up D1. As the Cloudflare account owner, use the D1 console to delete only authentication state:

DELETE FROM auth_sessions;
DELETE FROM system_settings WHERE key IN ('auth_password','phone_token_hash');

Set a fresh private SETUP_TOKEN in Worker secrets and run First-time setup again. Your tool records remain. Recreate the phone token and reconnect MacroDroid. This recovery requires your Cloudflare account; it is deliberately not a public password-reset endpoint.

What still needs a live check

  • Cloudflare resource bindings, account permissions, deployed CORS and cron execution.
  • Your API keys’ model access, real photo/PDF audits and provider rate-limit switching.
  • Your Android’s MacroDroid permissions, background polling, NewPipe notification format and overlay behavior.
  • Your bank’s exact SMS template. Unknown templates are rejected without adding a ledger entry.
  • Automatic Samsung Health energy extraction. Manual input works; the phone-side reader depends on your available Android integration.

Automated tests use real in-memory SQLite with provider responses mocked. The supplied app was not deployed or browser-tested in this build environment. See CHECKS.md for details.
